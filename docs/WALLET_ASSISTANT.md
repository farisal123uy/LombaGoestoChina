# Astra wallet assistant

The stage-two dashboard now supports English/Indonesian wallet requests alongside
the existing AI-to-AI procurement workflow. The implementation from
`feat/batching-evaluation` is integrated into the published `main` release.

## Capabilities

- **Asset overview:** the policy token's address, actual symbol/decimals, confirmed
  balance, native ETH balance, protected reserve, per-invoice cap, UTC-day budget,
  queued commitments and capacity available for a new plan. All amount arithmetic
  uses integers; figures are not generated by the model.
- **Payment management:** request a signed catalog invoice as a durable `draft`,
  review one to ten authenticated invoices, then queue the reviewed tasks. Quotes,
  recipient permissions, aggregate budget and policy are checked again. The existing
  worker performs the actual restricted-session execution and reconciliation.
- **Risk control:** report stale observations, inactive/expiring policy, contract
  pause, insufficient reserve/budget, overcommitted queue, expired invoices,
  unresolved operations and pending service delivery. Severity is deterministic.

This is one configured owner's smart account, one policy payment token and one
chain, not a multi-user portfolio/trading system. Market valuations, swaps, staking,
rebalancing, arbitrary-recipient transfers and policy administration are not exposed
as assistant actions. Native ETH is shown separately, not added to token purchasing
power. Zero ETH does not establish either missing or guaranteed paymaster sponsorship.

## Dashboard

After configuring the financial runtime in this worktree, start it and web in
separate terminals:

```powershell
npm.cmd run runtime:dev
# Second terminal, same repository root:
npm.cmd run dev:web
```

Use the ignored per-service configuration for this worktree; a Git worktree does not
automatically inherit another worktree's `.env` or `.local` session files. The existing
batching runtime requires database migrations through `0005`. This assistant adds no
new migration, contract deployment or owner/session permission.

Open `/dashboard`, sign in with the configured owner, and use **Your wallet, with
Astra**. The section is shown when `/v1/status.assistantConfigured` is true (Qwen,
asset reader and payment validator configured). A missing/unavailable model is an
error, not an unlabeled fallback to deterministic "AI".

Example instructions:

1. `Tampilkan aset saya dan sisa anggaran yang bisa digunakan hari ini.`
2. `Periksa risiko wallet dan pembayaran saya saat ini.`
3. `Sewa database 1 MB selama 1 jam sesuai kebijakan wallet saya.`
4. Select invoice checkboxes, then ask `Rencanakan pembayaran invoice yang dipilih.`

The assistant's procurement request stores a **draft**, even if scheduling is already
running. **Queue reviewed payments** releases only the reviewed task IDs. It leaves
the local pause flag unchanged; **Start agent** resumes the account queue, including
other queued tasks. Follow task/operation status and the transaction link for actual
settlement. `queued` is not a transaction receipt; `paid` is not verified delivery.

Draft quotes can expire. A new review rebuilds a short-lived plan while the signed
invoice remains valid. An expired invoice needs a new legitimate quote, not an
override of its signature/TTL. An existing submitted/unknown/confirmed invoice is
never released for a new operation by the assistant execution endpoint.

## API contract for frontend collaboration

All endpoints below require the existing owner login and `Authorization: Bearer`.
Browser-facing request/response types live in `packages/shared/src/assistant.ts`.
Existing procurement/task routes preserve their behavior; the new `draft` status is
additive and is intentionally excluded from worker claims and batch selection.

| Endpoint | Behavior |
| --- | --- |
| `GET /v1/assets` | `{ overview: WalletOverview }`; no model call or writes |
| `GET /v1/risk` | `{ overview, risk: WalletRiskReport }`; no model call or writes |
| `POST /v1/assistant` | Interpret a request and return overview/risk, optionally a draft and payment preview |
| `POST /v1/assistant/execute` | Revalidate and queue exact selected tasks; no signer access, no scheduler start |

Assistant request:

```json
{
  "requestId": "11111111-1111-4111-8111-111111111111",
  "instruction": "Plan payment of the selected authenticated invoices.",
  "taskIds": ["22222222-2222-4222-8222-222222222222"]
}
```

`taskIds` is optional for the assistant request. For payment previews it overrides
model-selected IDs; every ID is resolved against the authenticated owner/account.
Use a stable `requestId` when retrying the same procurement request after a lost
response. A changed goal needs a new ID. Reusing an invoice request ID with a different
goal returns `409`.

Execution request:

```json
{
  "taskIds": ["22222222-2222-4222-8222-222222222222"],
  "instruction": "Pay these authenticated invoices within my existing policy."
}
```

Execution returns `queued`, `blocked` with deterministic review blockers, or
`already_submitted` with existing tasks. If only some selected invoices already
have operations, the combined request is blocked; it does not partially queue the
rest. Concurrent queue releases use the account lock and recalculate commitments
inside a transaction; an intervening worker/queue change can return `409 TASK_BUSY`
or `QUEUE_BUDGET_CHANGED`. Refresh and review; do not create duplicate invoices.

Other errors: `401` unauthenticated/expired session, `404 TASK_NOT_FOUND` for unknown
or inaccessible task IDs, `400` invalid/duplicate IDs or extra authority fields,
`503` missing financial/model/asset/validator configuration. Do not treat an error
as an executed transaction or automatically call the old procurement route.

### Amounts and observations

Amount fields are decimal **integer strings**, timestamps Unix seconds. Format using
`overview.token.decimals`; do not hard-code six decimals for the assistant. Overview
includes the observed block/hash and policy version. Available capacity is:

```text
max(0, min(balance - reserve, daily cap - spent) - queued commitments)
```

Pending operations may already affect chain balances. Commitments are conservative
reservations, not an additional on-chain deduction. A payment preview includes all
other commitments before computing `balanceAfterUnits` and
`remainingDailyAfterUnits`; negative strings explicitly show a shortfall.
The risk report's scope is `wallet-policy-and-payment-operations`, not market risk.
Model interpretation is advisory text; only deterministic values and confirmed
receipts represent financial facts.

## Verification and evidence

```powershell
npm.cmd run test:integration
npm.cmd run model:wallet
$env:PLAYWRIGHT_PORT="3102"
npm.cmd run test:e2e
$env:KERNEL_FORK_RPC_URL="https://sepolia.base.org"
$env:WALLET_ASSISTANT_LIVE_MODEL="true"
$env:RECORD_WALLET_ASSISTANT_EVIDENCE="true"
npm.cmd run test:contracts
```

- Integration cases verify auth, exact decimals, draft/queue behavior, cumulative
  budget, concurrent releases, stale policy, invalid signatures and unknown operation
  handling, using PGlite and explicit model/chain fixtures.
- Browser cases verify the assistant and the original dashboard/setup using wallet/API
  fixtures; they do not broadcast.
- `evidence/wallet-assistant-model-baseline.json`: initial live Qwen corpus **11/12**.
  `wallet-assistant-model.json`: **12/12** after prompt refinement on the same corpus.
  This is selected in-sample regression evidence, not general injection immunity.
- `evidence/wallet-assistant-fork.json`: live Qwen intent/payment planning, owner-signed
  API login, PGlite, actual Kernel/EntryPoint/Guardian execution, lost-response
  reconciliation and repeated execution without a second send. The invoice payment
  changes the fork balance **9.74 -> 9.48** and UTC-day spending **0.26 -> 0.52**.
  Earlier setup includes a separate 0.26 activation payment. This is an isolated fork
  with ephemeral assets and a local stub bundler, not a new public payment.
